## 1. 收尾判据

合并这种事不能用「做得差不多了」来判断，否则会无限期拖下去。本轮用三条**可验证**的判据：

| 判据 | 内容 | 怎么验 |
|:--|:--|:--|
| **A｜没有独立缺陷了** | 剩余上游提交里，不再有「用户已经在踩、且不依赖未移植功能」的 bug | 逐条复核剩余 `fix` 类提交，每条要么「已修」，要么「本分支上该缺陷不存在」 |
| **B｜只剩成组功能块** | 剩下的是**加功能**，不是**修错**。不做不影响现有行为的正确性 | 每个功能块需 ≥5 个提交成组移植，且与上游 base 深度耦合 |
| **C｜只剩上游私有内容** | 品牌、版本戳、原型、格式化、文档 | 与本分支产品线无关 |

**满足 A 即收尾。** B 和 C 是「不做也不算欠债」的说明，不是待办清单。

本轮收尾时：A 已满足（见 §3 的逐条核实），剩余全部落在 B / C。

## 5. 以后想继续：从哪起

如果将来某个功能块真的需要了，**按块整体移植，不要按提交零敲**：

1. 先跑一次冲突勘查（本轮用的是 `git merge-tree --write-tree --merge-base=<c>^ dev <c>` 批量判定，
   再在临时 worktree 里 `cherry-pick -n` 数冲突块）。
2. 查这个块**依赖哪些更早的提交**——本轮踩过两次：`d4e3d74` 依赖 `43e6926` 的
   `pick_account(owner)`；`0aaf3ac` 依赖 `ff3dc28` + `f357a0d`。`merge-tree` 的「零冲突」
   **不代表能编译**。
3. 每应用一个提交就 `cargo check` 一次，别攒到最后。
4. 冲突取舍的默认方向：**本分支的 UI 结构更新**（品牌改造 + 两轮报障收敛），保留本分支；
   只把上游的**语义**接进去。

推荐起点（若只能做一件事）：**P13 降级链**。它是剩下唯一直接影响「上游挂了怎么办」的块，
而且本轮移植已经为它铺了路（`with_failover` 的挂载点、`sticky_key` 的位置都摸清了）。

## 7. 一条经验

**「能 cherry-pick」和「该 cherry-pick」是两件事。** 上游 254 个提交里，约 54 个能零冲突
机械应用，但其中若干打上去就编译失败（引用了尚未引入的类型），还有几个虽然编译通过、
功能却**没有真正生效**——最典型的是图片链路：协议层改完编译通过、测试通过，但数据层
仍把图片塞在顶层 `image_urls`，而 Qoder 上游只读 content 里的 `parts`。

判据必须是「行为变了没有」，不是「CI 绿了没有」。这也是本轮每批都要跑一遍
`cargo check --workspace --all-targets` + `tsc` + `npm run build` 的原因。
